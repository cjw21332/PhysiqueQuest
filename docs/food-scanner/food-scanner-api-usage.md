# Food scanner API usage and quotas

Set `GEMINI_API_KEY` and `USDA_API_KEY` on the backend. `GEMINI_MODEL` overrides the existing `gemini-3.6-flash` default. `FOODSCAN_RATE_LIMIT_ENABLED`, `FOODSCAN_RATE_LIMIT_MAX` and `FOODSCAN_RATE_LIMIT_WINDOW_MS` control the shared fixed window. All replicas must use the same settings and database. The scanner also has configured image, request, provider timeout and retry limits. Never put provider keys in client code or reports.

Each authenticated scan reserves a `food_scan_usage` record keyed by a hash of the authenticated user and normalized request ID before running analysis. Background nutrition jobs use their job ID as the request ID and reserve before the provider call as well. An existing reservation rejects the duplicate; retries need a fresh request ID. A record stores user ObjectId, request ID, timestamp, model, provider, outcome, safe error category and available token counts. Failed calls with no usage metadata retain null counts; a failed retry marks the scan's known token counts as partial. Completion writes retry once. A per-instance maintenance worker atomically marks stale pending records `incomplete` without inventing an outcome; a later completion can resolve them. `FOODSCAN_USAGE_STALE_MINUTES` defaults to 30 (minimum 10); `FOODSCAN_USAGE_RETENTION_DAYS` defaults to 90. Only resolved records with complete usage are removed after that interval; pending, incomplete and records with unknown usage remain for operator review. Account export and purge use the same user ObjectId, and reservation checks active account status before and after insert. Review remaining races across account deletion and other user-data writes before production.

Authenticated `GET /api/nutrition/scan-usage` returns the current user's aggregate counts over records still retained; these are not lifetime totals after cleanup. Token totals are null when no counts exist, with known-count and partial indicators; they are not a billing statement. Estimated cost is null: pricing, image accounting, retries, thinking and cached-token billing are not sufficiently captured here to calculate a reliable cost. Consult current official pricing and provider billing data before introducing a versioned calculation.

The maintenance log emits pending/incomplete counts, oldest unresolved age, reconciliation and deletion counts, and process-local failed-completion-write count without user identifiers. These are not a durable global monitoring system; aggregation and alerting are still required. Each successful/failed completion only updates pending/incomplete records, so repeated completion cannot add tokens twice. Database failure can leave a pending record that later becomes incomplete; the system cannot reconstruct an unavailable provider response.

The web review now persists a user-scoped key and original meal payload before submitting and can query `GET /api/nutrition/meals/from-scan/receipts/:key`. A confirmed receipt is returned only for the authenticated owner; an unknown result does not distinguish failure from an in-flight write. Recovery retries the unchanged request with the same key. Web Locks serialize tabs; without them the protected path refuses to submit. Storage contains meal details but no photo and persists until confirmation. Logout, browser storage deletion, private browsing, unsupported browsers, or another device can prevent recovery.

Google's [Gemini Developer API pricing](https://ai.google.dev/gemini-api/docs/pricing) lists separate rates and time-dependent changes for `gemini-3.6-flash`; output pricing includes thinking tokens. These published prices alone do not establish the account's tier, the missing usage of failed requests, or the amount billed for this scanner. No per-scan dollar estimate is produced.

From `backend/`, after building, `node --env-file=.env scripts/foodscan-live-smoke.mjs --live` makes real provider calls and may incur charges. It uses a synthetic 1-pixel PNG and a USDA query, prints only sanitized status and usage, does not save a meal, and is a connectivity/schema check rather than an accuracy benchmark. The direct smoke test bypasses the authenticated API usage ledger. Use a test account and isolated environment for full API checks.

On 2026-11-15 (Asia/Singapore), the synthetic-image Gemini call to `gemini-3.6-flash` timed out; no usage metadata was received. The live USDA search returned three candidates, the first record (`169711`) returned all four requested macro fields, and a deliberately invalid ID returned `NOT_FOUND`. These observations do not verify actual food recognition, live USDA rate limiting or reliable provider availability.

Follow-up staged tests: simple Gemini text timed out after 20,062 ms, independent synthetic image input after 20,008 ms, and structured scanner output after 20,022 ms. DNS resolved. An authenticated scanner HTTP request against isolated MongoDB returned 504 after 20,212 ms and recorded failure with unavailable usage. The text failure means the image prompt alone does not explain the problem; authentication, network path and provider availability remain unproven. No timeout increase or model change was justified. Diagnostic modes are `--mode text`, `image`, `structured`, `app` and `usda`; `app` needs `FOODSCAN_DIAGNOSTIC_URL` and `FOODSCAN_DIAGNOSTIC_TOKEN` for an isolated test account. A local opt-in test in `test/foodscan-live.e2e-spec.ts` exercises the real scan route with a synthetic image and live providers.

Additional diagnostics returned HTTP 404 from an unauthenticated Google API root HEAD in 149 ms and HTTP 200 from the configured model metadata endpoint in 223 ms using the configured key. A direct REST text-generation request also timed out after 20,018 ms. Subsequent direct REST and SDK text, synthetic image, structured output and authenticated synthetic-image scan requests succeeded; see [Gemini troubleshooting](food-scanner-gemini-troubleshooting.md). Thus the timeout was intermittent, and its precise cause remains unresolved. The script also offers `--mode metadata` and `--mode rest-text` for reproducible checks.

An expanded live USDA check initially selected a glutinous record for generic cooked white rice. After adding a conservative variety guard, the automatic lookup selected medium-grain cooked white rice (`168930`), raw chicken breast (`2646170`), and fried egg (`173423`) for those respective test queries. Manual candidate search still presents alternatives, including glutinous rice, for user review. These three examples do not establish general matching accuracy.

For idempotent meal saves, send `idempotency_key` (16–80 letters, digits, `_` or `-`) with an unchanged body. The server stores the key, payload hash and resulting meal IDs in the user's nutrition document atomically with the rows. Same-key retries return the same receipt; a different body under that key returns 409. Unique `nutrition.userId` indexing is required. Legacy requests without a key remain accepted but are not protected; clients must migrate. Receipts are not automatically deleted; capacity and retention require operational review.

An opt-in isolated MongoDB test is available with `PQ_TEST_MONGO_URI` set to a test server: `npm run test:e2e -- --run test/foodscan-persistence.e2e-spec.ts`. It creates and drops only a uniquely named `pq_foodscan_test_…` database. Provider calls are mocked. It covers authenticated backend routes and saved data, plus shared quota and ledger operations; it does not use a real browser or real providers.
# Lifecycle caveat (2026-11-15)

Provider usage tracking does not by itself fence all writes against account
deletion. See `account-deletion-lifecycle.md` before deployment. Late usage
completion updates existing records without an upsert, but this is not proof
that every scan or background-job path is safe against deletion races.
