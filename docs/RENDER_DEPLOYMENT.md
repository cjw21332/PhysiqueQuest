# Render staging and Android release setup

Configuration prepared October 18, 2026. No Render service has been provisioned and no Android binary has been published.

The frontend prebuild hook now prepares the pinned [RepDB in-app guides](REPDB_LIBRARY.md). A clean build needs outbound access to Hugging Face; generated catalog data remains ignored and must not be published as a dataset/API.

## Services

Import the repository as a Render Blueprint using `render.yaml`. It defines two Node 22 web services: Next.js web and a shared NestJS API for accounts, workouts, exercise browsing and Coach plans. The blueprint uses free staging plans; sleeping services have cold-start delays and must not be treated as reliable production safety delivery. Choose measured always-on capacity before production.

Render assigns public HTTPS service URLs. Supply these exact values after service creation:

| Service | Variable | Value |
|---|---|---|
| API | MONGODB_URI | Dedicated staging Atlas URI with transactions/replica-set support and network access configured for the Render backend. |
| API | JWT_SECRET | Generated by the blueprint. Keep stable across deployments; rotating it invalidates login tokens and outstanding recovery codes. |
| API | FRONTEND_URL | Public web service origin, such as https://your-web.onrender.com; no trailing route. |
| Web build | NEXT_PUBLIC_API_URL | Public API service URL plus /api. |

Rebuild the web service after changing NEXT_PUBLIC variables. Do not use Render's private service `host`/`hostport` in browser URLs. Their private network names are not reachable by an Android phone. Provider keys are configured on the API service only, using the existing backend environment examples; never in NEXT_PUBLIC or EXPO_PUBLIC variables.

Health checks: `/launch` for web and `/api` for the shared API. Public library routes are `/api/exercises` and `/api/exercises/:id`; saved programs remain authenticated at `GET /api/coach/plan`. Verify the public URLs and CORS from the exact hosted web origin. Set the trust-proxy-hop setting to match the actual deployed proxy chain before relying on per-IP limits; do not accept arbitrary client-forwarded IPs.

Rebuild the frontend with `NEXT_PUBLIC_API_URL` pointing to the shared API. Retire the old library URL and `NEXT_PUBLIC_COACH_API_URL` configuration. Existing deployed services are not removed by editing this blueprint: verify the new frontend and routes first, then retire an old library service through the hosting dashboard. This task has not changed any live Render service.

## Android configuration

`mobile/app.config.js` preserves LAN development defaults but rejects missing, private-LAN or non-HTTPS endpoints when PQ_RELEASE_MODE=true. The preview and production profiles in mobile/eas.json enable this guard. Supply EXPO_PUBLIC_WEB_APP_URL and EXPO_PUBLIC_API_URL in the corresponding EAS environment before building. Preview creates an internally distributed APK; production uses the store distribution profile. EAS project association, account access and signing credentials remain to be configured by the project owner. Keep keystores and service credentials outside Git.

Install a signed preview APK and verify it on mobile data: startup, login, recovery, exercise library, session completion/reload and account isolation. Hermes export is not a native release build. Foreground-only safety monitoring must be clear in the app and tested on the phone; do not claim protection while locked/backgrounded.

## Recovery rollout

The new reset endpoints require requestId for code verification and resetToken for confirmation. Deploy backend and frontend as a coordinated release; code-only clients must update. Old recovery documents have no requestId/grant and are unusable by the new path. Back up the database and invalidate old outstanding recovery records through an explicit reviewed migration before rollout; no live records were deleted by this change.

New fields/indexes: users.sessionVersion (missing interpreted as 0), request/grant/attempt fields in password_recovery_tokens, and auth_rate_limits with TTL buckets. Grant consumption, password update, session-version increment and recovery invalidation use one MongoDB transaction. MongoDB standalone without transaction support is not a supported recovery deployment; failure must roll back, not partially reset an account. Verify indexes and transaction behavior on staging.

No vulnerable code-only fallback should be restored during rollback. Unaffected legacy login tokens are accepted as version 0 until a reset increments that user's version.

## Release gates

Do not mark deployment complete until the signed Android installation, real provider tests with controlled contacts, persistent database read-back and rollback rehearsal pass. Pose detection, repetition counting and supported experimental form feedback belong on the user device. Do not deploy a separate pose-analysis service or configure POSE_ANALYSIS_URL / POSE_ANALYSIS_API_KEY for this release. Render hosts the frontend and one shared API, including exercise browsing. Keep manual logging available when a local check cannot be assessed reliably.
