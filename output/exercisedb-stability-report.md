# ExerciseDB stability verification — 6 November 2026

The meal and nutrition test failures were caused by test-only loaders: one evaluated a CommonJS component using `require` relative to the test file instead of resolving the component's relative imports; the other loaded transpiled ESM from a data URL, which cannot resolve `./nutrientTotal`. Both harnesses now resolve those real dependencies without changing application behavior. The five formerly failing cases passed individually and the complete frontend Node suite passed.

The hard-stop verification used a separate local MongoDB database and synthetic fixtures. Two pages were checkpointed, then a third logical `bulkWrite` was deliberately paused after one real upsert and its worker process was forcibly terminated. The saved checkpoint still pointed to page three, with four checkpointed and five actually stored records. After the original 60-second lease expired, a new process retried the page and finished with six unique records; all five existing records were retained. This tests interruption during an unfinished logical bulk operation, although it does not force MongoDB itself to terminate during an individual server-side write. Real production/user data was not modified by the crash test.

The prior per-record audit found 176 HTTP 404 GIFs. Three were rechecked against the official ExerciseDB detail endpoint and the official original GIF URL: all three detail records still supplied the same original URL, and all three GIF GETs still returned 404. The [official V1 documentation](https://oss.exercisedb.dev/docs) describes a single `gifUrl` and does not document an alternate per-exercise media URL. No legitimate official replacements were identified, and permanence cannot be determined from these checks. All 176 IDs, names, original URLs and observed statuses are recorded in `exercisedb-unavailable-media.json`; no substitute media was assigned.

The viewed-media cache is local to each browser, contains only demonstrations whose image load succeeded, retains at most six entries, and skips additions when reported storage is at least 80% full. The provider does not expose CORS headers for the sampled GIF, so cross-origin responses are opaque: the browser's successful image-load event is used before retaining a candidate response. Opaque responses cannot be independently inspected by the service worker. A Chromium persistent-profile test loaded a real provider GIF, closed the browser, reopened with networking disabled, and rendered that cached GIF. A separate test loaded seven real provider demonstrations and verified that the oldest was evicted. Storage-quota exceptions in IndexedDB were simulated; the exercise library remained usable.

The mobile and tablet checks used Chromium device-size and network emulation, not a physical device. Tests used 360-, 390-, and 768-pixel viewports, 150 ms network latency with throttled throughput, a 100-character search, simultaneous filters, repeated details, offline mode, and simulated IndexedDB quota failure. A Chromium quota override also prevented a GIF cache write while the demonstration still loaded online. The library retained its paginated rendering and did not fetch GIFs while merely loading the list. The last 390-pixel run measured 1,189 ms to first exercise, 381 ms offline search including debounce, 34 ms combined filtering, a 16.7 ms 95th-percentile scrolling frame interval, and approximately 17.1 MB reported JS heap. Storage estimates were 1,552,855 bytes IndexedDB and 4,261,312 bytes total Cache Storage after viewing a GIF; opaque-response quota accounting makes the latter an estimate rather than a GIF file size. The previous no-GIF run measured 1,383 ms, 441 ms, 40 ms, 16.8 ms, 11.9 MB heap, 1,546,261 bytes IndexedDB, and 368,896 bytes Cache Storage. These single runs are not controlled benchmarks; see `exercisedb-offline-performance.json` for the latest measurements.

The complete frontend Node suite passed 158/158, with each of the five previously failing cases also run individually. The complete backend suite passed. The exercise library and offline media Playwright suite passed 17/17. Other browser suites were not run in this pass; actual account login, physical-device behavior, and existing user data were not exercised.

Provider restrictions remain applicable: the [free V1 API](https://oss.exercisedb.dev/docs) is limited to non-commercial/personal/educational use, requires attribution, and applies strict rate limits. GIF availability and browser storage are not guaranteed. The simulated quota failure does not prove behavior on every device or browser.
