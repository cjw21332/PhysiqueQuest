# ExerciseDB readiness verification — 6 November 2026

The configured application catalog reported 1,500 provider records and 1,500 unique stored IDs. An API pagination check read all 1,500 unique IDs. The application database and the isolated audit database were compared by provider ID and GIF URL: 0 missing IDs, 0 differing URLs, and 0 missing GIF URLs. The catalog worker uses `MONGODB_URI` by default and stores its data in dedicated catalog collections; the same-origin frontend proxy reached this catalog.

The serial media audit sent one HTTP HEAD request at a time with a minimum 1.2-second interval. Of 1,500 URLs, 1,324 returned HTTP 200 with `image/gif` and 176 returned HTTP 404. There were 0 invalid URL formats, redirects, successful responses with unexpected content types, or unverified requests. These are HTTP response observations at the time of the audit; they do not establish that all successful GIF bodies render. Three successful provider samples rendered in Chromium. A separate GET confirmed one observed 404. The per-ID observations are in `exercisedb-media-audit.jsonl`; no GIF bodies were saved.

An isolated MongoDB recovery check saved a cursor after two fixture records, simulated a 429 with a 120-second Retry-After, timeout, and network error, and then resumed from that cursor in a new process. The worker completed with three distinct fixture records. This tests interruption between pages and failure recovery; it does not prove behavior for an operating-system kill during an in-flight database write.

The production-build browser test populated IndexedDB from the configured catalog, closed and reopened a persistent browser profile with networking disabled, searched and combined body-part, target-muscle and secondary-muscle filters, changed sorting, opened cached details, and reconnected. It observed a renewed synchronization-status request. Account API responses were stubbed in this test; the catalog API and provider GIF samples were real. Cache Storage was checked to contain only the public offline shell assets. The test checked that opening and synchronizing the list requested no GIFs.

At a 390×844 Chromium viewport, one local run measured 1,383 ms to the first exercise, 9,420 ms to populate the device catalog, 441 ms for offline search including debounce, 40 ms for combined offline filtering, and a 16.8 ms 95th-percentile scrolling frame interval. Chromium reported approximately 1,546,261 bytes of IndexedDB storage, 368,896 bytes of Cache Storage, and 11.9 MB of JavaScript heap. These are single desktop-browser measurements, not physical-phone benchmarks.

Verification: the backend build and complete backend suite passed (96 files, 2,452 tests); frontend production build and TypeScript check passed; 13 targeted exercise-library browser tests passed; seven frontend authentication/workout Node tests passed. The broad frontend Node test command had 153 passes and five failures in nutrition/meal test harnesses: one could not resolve `../Scan/AdditionalNutrition`, and four data-URL tests could not resolve `./nutrientTotal`. Their output is in `exercisedb-frontend-tests.tap`.

Remaining limitations: GIF availability may change and 176 provider URLs returned 404 during this audit; offline GIFs are available only if the browser already has them. A full catalog reconciliation does not automatically delete provider records removed from the source; a provider-total mismatch is instead treated as a failed sync to avoid deleting data. Browser storage can be evicted. The offline experience is a public library shell, not offline access to account data or workout mutations. Tests did not measure a physical mobile device, validate an actual user login, or kill a worker mid-write.
